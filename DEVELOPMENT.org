* Development

Source of the photography portfolio hosted at [[https://andreypudov.com][andreypudov.com]]. The site is a
Next.js application exported as a fully static website and served by GitHub
Pages. Next.js and React are used only at build time: the published pages are
plain HTML and CSS, with a few small scripts where a page needs them.

** Project structure

| Path                  | Purpose                                                                 |
|-----------------------+-------------------------------------------------------------------------|
| =src/app/=            | Pages (App Router): home, =portfolio/=, =about/=, =contact/=, =ip/=, =time/= |
| =src/app/sitemap.ts= | Generates =sitemap.xml= at build time, dated with the build              |
| =src/components/layout/= | Shared layout: header, footer, analytics                             |
| =src/components/ui/=  | Abstract UI blocks: carousel, feature/masonry/image grids, lightbox     |
| =src/lib/=            | Build-time helpers: album metadata lookup, WebP dimension reader        |
| =src/styles/=         | Hand-written CSS, one file per abstract component, combined in =site.css= |
| =data/photographs/=   | Album metadata (JSON): name, description, path, orientation, date       |
| =data/schemas/=       | JSON schemas describing the album format                                |
| =public/media/=       | Full-resolution photographs, =thumbnails/= (downscaled variants), other images |
| =public/=             | Files copied as is: =CNAME=, =robots.txt=, =.well-known/=                 |
| =public/scripts/=     | Plain browser scripts: analytics, world clock (=/time=), network info (=/ip=) |
| =scripts/=            | Build tooling: =build-thumbnails.sh= (with its sRGB profile), =strip-runtime.mjs= |
| =services/=           | Standalone Go services backing the =/ip= and =/time= pages              |
| =.github/workflows/=  | GitHub Actions workflow that builds and deploys the site                |

Pages select photographs by file name (e.g. =2025-12-06_015.webp=), see the
=CAROUSEL= and =FEATURE_GRID= lists in =src/app/page.tsx= and =SECTIONS= in
=src/app/portfolio/page.tsx=. At build time =src/lib/photographs.ts= resolves
each name against =data/photographs/*.json= for its caption and reads image
dimensions directly from the WebP files. Grids and other small images are
served through =srcset=, so browsers download a downscaled variant instead of
the original (see [[*Thumbnails][Thumbnails]]).

** Development

Requirements: Node.js 22 or newer, npm and ImageMagick (only to build
thumbnails).

#+begin_src shell
npm install          # install dependencies
npm run dev          # development server on http://localhost:3000
npm run typecheck    # TypeScript check without emitting files
npm run thumbnails   # build missing image variants (see Thumbnails)
npm run build        # static export into out/, without the JS runtime
#+end_src

The project uses =output: 'export'=, so =next start= is not available. To
preview the production build, serve the =out/= directory with any static
server:

#+begin_src shell
npm run build
npx serve out        # or: python3 -m http.server -d out 3000
#+end_src

*** Adding photographs

1. Put the full-resolution image into =public/media/photographs/<album>/=.
2. Describe the image in the matching =data/photographs/<album>.json=.
3. Reference the file name in the page's list (homepage or portfolio).
4. Run =npm run thumbnails= and commit the generated files together with
   the photograph.

The build fails with an explicit error when a referenced photograph has no
metadata, or when its file or one of its variants is missing, so
=npm run build= doubles as a check.

** Static output without JavaScript

=npm run build= runs =next build= and then, as npm's =postbuild= hook,
=scripts/strip-runtime.mjs=. Every page is rendered completely at build
time and links are plain =<a href>= elements, so each page lives in its own
=<route>/index.html= and navigation never needs JavaScript, just like the
previous site. The Next.js runtime would only hydrate React on pages that
are already complete, so the script removes it:

- =<script>= elements loading =/_next/= chunks, and the inline React Server
  Components payload (a second copy of every page),
- script preload hints, React hydration markers and the empty metadata
  =<div hidden>=,
- the JavaScript chunks, build manifests and client navigation data
  (=*.txt=) that nothing references afterwards.

The stylesheet (=/_next/static/chunks/*.css=) and scripts from
=public/scripts/= are kept. The script then verifies every page and fails
the build if any runtime reference remains, so a change in the Next.js
output format cannot ship half-stripped pages. This removes about 560 KB of
JavaScript from every page and roughly two thirds of the HTML (the homepage
goes from 255 KB to 93 KB).

Consequently, components must not rely on client-side React: no ='use
client'=, hooks, event handlers or =next/link=. Behaviour that needs the
browser is written as a plain script in =public/scripts/= and included by
the component with =<script type="module" src="/scripts/…">=; the component
renders the markup the script fills in (see =WorldClock.tsx= and
=world-clock.js=). Elements the script changes are marked with
=suppressHydrationWarning=, because =npm run dev= still hydrates the pages.

** Thumbnails

=scripts/build-thumbnails.sh= is a POSIX shell script built on ImageMagick
(version 7 =magick=, or version 6 =convert= and =identify=). It replaces the
thumbnail step of the previous Python engine.

#+begin_src shell
npm run thumbnails                    # every image referenced from src/
npm run thumbnails -- 2025-12-06_015.webp /images/covers/bank_of_russia.webp
npm run thumbnails -- -f              # regenerate existing variants too
#+end_src

Without arguments the script collects every =.webp= name mentioned in
=src/=, so only images that are actually rendered get variants. Existing
files are skipped, which makes repeated runs cheap. The variants are
committed, so neither the CI build nor other contributors need ImageMagick.

*** Variants

| File                 | Size                        | Used for                                     |
|----------------------+-----------------------------+----------------------------------------------|
| =<name>_300.webp=    | fits into 300×300           | low-quality placeholder shown while loading  |
| =<name>_400w.webp=   | 400px wide                  | =srcset= candidate                           |
| =<name>_800w.webp=   | 800px wide                  | =srcset= candidate                           |
| =<name>_1200w.webp=  | 1200px wide                 | =srcset= candidate                           |
| original             | 2048px long edge            | last =srcset= candidate, carousel, lightbox  |

Photographs keep their variants in =public/media/thumbnails/=, mirroring
=public/media/photographs/=. Other images (e.g. =images/covers/=) keep them
next to the original. Variants that would be as wide as the original or wider
are not created.

The widths follow the layouts: grid tiles are rendered 200–380 CSS pixels
wide on desktops and up to the full screen width on phones, so 400px covers
standard displays, 800px high-density displays and 1200px phones rendering a
single column at 3× density. Each component states its rendered width in a
=sizes= attribute (derived from its stylesheet) and the browser picks the
smallest sufficient candidate. The carousel fills the viewport height, which
=sizes= cannot express, and the lightbox shows photographs at full size, so
both keep the original. The widths are defined in the script (=WIDTHS=) and
in =src/lib/photographs.ts= (=VARIANT_WIDTHS=) and must be kept in sync.

*** Conversion settings

| Setting                                  | Reason                                                                                                 |
|------------------------------------------+--------------------------------------------------------------------------------------------------------|
| =-auto-orient=                           | Applies the EXIF orientation before the metadata is stripped.                                         |
| =-intent Relative -black-point-compensation -profile sRGB.icc= | Converts wide-gamut originals into sRGB (see below).                            |
| =-strip=                                 | Removes EXIF, XMP and ICC data: about 37 KB per file, including camera serial numbers and locations.   |
| =-filter Lanczos -resize=                | Sharp downscaling without visible ringing; =>= and the width checks prevent upscaling.                 |
| =-quality 85=                            | Balance between size and fidelity chosen by measurement (see below).                                  |
| =-define webp:method=6=                  | Slowest, most thorough encoder search: smaller files at the same quality, only paid once per image.    |
| =-define webp:use-sharp-yuv=true=        | More accurate RGB→YUV conversion that keeps saturated colour edges crisp, for about 5% more bytes.     |

*Colour management.* Most originals are sRGB, but about 170 of them carry
Adobe RGB, ProPhoto RGB or Display P3 profiles. Stripping the profile of such
an image without converting it makes browsers interpret it as sRGB, and it
looks washed out: on a ProPhoto RGB sample the mean saturation dropped from
0.24 to 0.14. The script therefore converts every image into sRGB first,
using relative colorimetric intent with black point compensation (the
intent supported by the matrix-based profiles involved), and only then strips
the profile. The sRGB IEC61966-2.1 profile is stored in
=scripts/profiles/sRGB.icc= so the conversion does not depend on system
paths. The originals keep their profiles, so the lightbox remains
colour-managed.

*Quality.* Measured on five representative photographs against a lossless
downscale (SSIM, higher is better):

| Quality         | 400w size | 800w size | 800w SSIM |
|-----------------+-----------+-----------+-----------|
| 75              | 21 KB     | 72 KB     | 0.973     |
| 80              | 26 KB     | 88 KB     | 0.978     |
| 80 + sharp YUV  | 28 KB     | 92 KB     | 0.979     |
| 85 + sharp YUV  | 34 KB     | 112 KB    | 0.982     |
| 88 + sharp YUV  | 39 KB     | 130 KB    | 0.985     |
| 90              | 40 KB     | 140 KB    | 0.985     |

85 with sharp YUV is where further quality costs noticeably more bytes for
little visible gain, while staying close to the originals (exported at 92).
An 800px variant is about a fifth of its original (~550 KB). Sharpening
after resizing (=-unsharp=) was evaluated and left out: it grew files by
about 25% and moved them further from the source.

** Deployment to GitHub Pages

Deployment is automated by =.github/workflows/deploy.yml=. Every push to
=master= (or a manual run via /Actions → Deploy to GitHub Pages → Run
workflow/) does the following:

1. installs dependencies with =npm ci=,
2. runs =npm run build= to produce the static site in =out/=,
3. uploads =out/= as a Pages artifact and publishes it with
   =actions/deploy-pages=.

One-time repository setup: /Settings → Pages → Source: GitHub Actions/. The
custom domain is taken from =public/CNAME=.

The build output is never committed. =master= contains only sources and
media; =out/= and =.next/= are ignored by git. Committing the output to
=master= (as the previous Python engine did) would mix generated files with
sources and produce noisy diffs, and pushing it to a =gh-pages= branch would
store every photograph a second time, growing the repository with each
deployment. A Pages artifact keeps the output outside git entirely.
